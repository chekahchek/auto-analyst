# Alembic Migrations — Design Spec

**Date:** 2026-06-07  
**Task:** 2.2 — Set up Alembic for migrations  
**Status:** Approved

---

## Context

Task 2.1 (SQLModel schema) is complete. The backend has four models (`User`, `Dataset`, `Session`, `Message`) with a shared `UUIDBase` + `TimestampBase`. The app uses an async SQLAlchemy engine (`postgresql+asyncpg://`). Alembic must be added to manage schema migrations going forward.

---

## Goals

1. Initialise Alembic in the `backend/` directory.
2. Configure it to use a **sync** driver (`psycopg2`) derived from the existing async DB URL.
3. Generate the first migration covering all existing models.
4. Provide a convenient but safe way to run migrations in local dev.
5. Ensure tests run against the migrated schema.

---

## Architecture

Alembic runs with a sync engine that is completely separate from the app's async engine. No changes to `app/database.py` or the models.

```
backend/
├── alembic/
│   ├── versions/          # migration scripts
│   ├── env.py             # Alembic runtime (sync engine)
│   └── script.py.mako     # migration template
├── alembic.ini            # Alembic configuration
├── app/
│   └── config.py          # + sync_db_url property
├── docker-compose.yml     # + optional migrator service
└── tests/conftest.py      # + apply_migrations fixture
```

## Configuration

### `app/config.py`

Add a computed `sync_db_url` property:

```python
@property
def sync_db_url(self) -> str:
    """Return a sync-driver URL for Alembic / admin tools."""
    return self.db_url.replace("postgresql+asyncpg", "postgresql+psycopg2")
```

### `alembic.ini`

Generated by `alembic init`, trimmed to essentials. Key settings:

- `script_location = alembic`
- `prepend_sys_path = .`
- `version_path_separator = os`

Log levels: `WARN` for SQLAlchemy engine, `INFO` for Alembic.

### `alembic/env.py`

- Import `app.models` so `SQLModel.metadata` is populated before Alembic inspects it.
- Set `sqlalchemy.url` from `Settings.sync_db_url`.
- Support `run_migrations_online()` (CLI default) and `run_migrations_offline()` (SQL generation).
- `target_metadata = SQLModel.metadata`

## docker-compose Integration

Add a `migrator` one-shot service to `backend/docker-compose.yml`:

```yaml
  migrator:
    build:
      context: ..
      dockerfile: backend/Dockerfile
    command: ["sh", "-c", "cd backend && alembic upgrade head"]
    depends_on:
      db:
        condition: service_healthy
    environment:
      APP_ENV: dev
    volumes:
      - ..:/app
    profiles: ["migrate"]
```

**Profile usage:** `docker compose --profile migrate up migrator`

The profile prevents accidental auto-runs. The container exits after completing the migration.

## First Migration Workflow

```bash
cd backend
alembic revision --autogenerate -m "Initial schema"
alembic upgrade head
```

This produces a single migration script covering `users`, `datasets`, `sessions`, and `messages` tables with their indexes and constraints.

## Testing Integration

Add a session-scoped, autouse fixture in `tests/conftest.py`:

```python
import pytest
from alembic.config import Config
from alembic import command

@pytest.fixture(scope="session", autouse=True)
def apply_migrations():
    alembic_cfg = Config("alembic.ini")
    command.upgrade(alembic_cfg, "head")
```

Tests always run against the migrated schema. No `create_all()` calls.

## Error Handling

| Scenario | Handling |
|---|---|
| Migration fails | `migrator` exits non-zero; docker-compose shows failure; logs to stderr |
| DB unreachable | `depends_on` with `condition: service_healthy` blocks until Postgres is ready |
| URL mismatch | `sync_db_url` is covered by a unit test ensuring `asyncpg` → `psycopg2` |
| Missing migration | `alembic check` (or `alembic current` vs `alembic heads`) surfaces drift |

## Dependencies

Add to `pyproject.toml` dev group:

```toml
[dependency-groups]
dev = [
    # ... existing ...
    "alembic>=1.15.0",
    "psycopg2-binary>=2.9.10",
]
```

`psycopg2-binary` is used instead of `pg8000` because it is the standard, battle-tested choice and build issues are rare in local dev / Docker.
